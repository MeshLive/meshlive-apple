# Experimental, alternative and optional behaviour: the switch register

Every behaviour that can be switched, and every alternative that was kept, with its default and why. New behaviour
that is not yet proven ships **off by default**, labelled Experimental, and gets a row here. The losing side of a
comparison stays switchable instead of being deleted. Android's register
([meshlive-android switches](https://github.com/MeshLive/meshlive-android/blob/main/docs/dev/switches.md)) owns the
shared protocol switches; the Android names are given where a switch mirrors one.

Settings paths are the iPhone's; the Mac app uses the same Settings pages in its sidebar and Settings window.

Launch arguments take `YES`/`NO` (or `1`/`0`). A switch with a Settings row also accepts its key as a launch argument
in every build. A switch without one (a control arm or a lab experiment, named "launch argument" below) is read only
by DEBUG builds; a release build always runs the default shown here, as Android honours its `test_*` extras only in
debug builds.

| Item | Default | Switch / reason |
| --- | --- | --- |
| Keep the call camera running while it is off (control arm) | Off | Launch argument `-NearbyKeepCameraWhenOff 1` restores the old behaviour: Video off stopped sending but kept capturing, so the camera light stayed on (seen on the Mac: `cameraOn=false`, `cameraRunning=true`). Default on iPhone and Mac: Video off releases the camera; Video on starts it again with a fresh keyframe, as returning from the background already did |
| iPhone link timer in default run-loop mode (control arm) | Off | Launch argument `-NearbyDefaultModeLinkTimer 1` restores the old 0.1 s link tick scheduled in the default run-loop mode, which pauses while a scroll or held control tracks touches. Default: common modes, as the Mac's `DesktopConnectionTimer` (that stall was measured on the Mac; the iPhone scroll stall is inferred from Apple run-loop rules, not yet measured). |
| Native Mac Android compatibility | Off | macOS: Settings › Advanced › Experiments › "Android compatibility" (`experimentalDesktopAndroidCompatibility`). Accept rotating offers independently of this Mac's advertised ID; use the existing BMH3 call path, per-attempt pseudonym and offer-opening checks. Enables BMH3 responder parsing. iPhone runtime and protocol core are unchanged. Physical GATT voice calls and calls selected by generated names worked; video calls with a Galaxy S24 still drop when the phone's incoming data stops ([testing](testing.md#hardware-results-release-app-mac-with-android-phones-over-gatt)). |
| Native Mac hardware-free preview (DEBUG only) | Off | Explicit `-NearbyPreview`: ephemeral identity, isolated preferences and Bluetooth/media off. Startup skips the legacy presence-key cleanup as well as current Keychain reads/writes. It is a UI aid; normal automation arguments use the real runtime. |
| Native Mac unattended interop arguments (DEBUG only) | Off | `-NearbyEphemeralIdentity 1` keeps the identity and presence state in memory for that run, so a freshly built, differently ad-hoc signed Debug app never waits on a login-Keychain access prompt; radio, media and protocol paths are the normal runtime and the identity is new each launch. `-NearbyCallCamera off` switches the Mac camera off as soon as a video call is active, for receive-only video checks that must not show the room (logs `auto_camera`). Release builds ignore both |
| Standalone v1 protocol (Noise XX, X25519/ChaChaPoly, 40-bit SAS; iPhone-to-iPhone only) | Off | `NearbyV1Experimental` library and tests, the Java reference (`Scripts/interop.sh`), and the old app via `python3 Scripts/project.py --v1-experiment`. Kept as the losing alternative; it cannot talk to Android |
| Call video fragments (Android's experiment, BME1 type 9) | Off | `CallEngine(videoFragments:)`. Only useful when the Android peer enables `test_call_video_fragments` |
| H.264 codec (addendum B) | Not built | Pending Android review of addendum B (B2-B6); the iPhone uses VP9 |
| Connection type | Standard (GATT) | Settings › Connection (`transport`): "Faster channel (L2CAP)" offers calls and streams over an L2CAP channel; Standard works with every supported device |
| Identity mismatch policy | Refuse | Settings › Privacy › Advanced privacy › "Warn instead of refusing an identity mismatch" (Android `MismatchPolicy.WARN`) |
| Names and titles (peer labels, naming phase 1) | Off | Settings › Privacy › "Names and titles", like Android's `test_peer_labels`. BNL1 signed labels in a BLB1 container (BME1 type 10), negotiated by end-to-end hello bit 5; title pages (version 3) are read, not sent |
| Readouts at condensed width | Off | `TokenType` keeps Android's declaration for reference only; the iPhone uses Dynamic Type text styles |
| Discovery rows keyed by node prefix | On | `DiscoveryTable` (rows by prefix + kind + route token, 8 s expiry, one rediscovering retry). Replaced per-peripheral rows, which left stale duplicates when Android rotated its advertising address |
| Default call and stream video | 426x240 (portrait 240x426), 15 FPS, 200 kbps | `MediaDefaults` (design decision 2026-10-10, as Android, which also offers 360p/480p); the resolution ladder steps down from it on weak links |
| Call resolution ladder | On (user calls) | `CallResolutionLadder`: WebRTC start limits; the portrait 240x426 call steps to 180x320 below 120 kbps and back with hysteresis (keyframe restart, header unchanged). DEBUG `-NearbyResolutionLadder 0` turns it off, as Android benchmark launches |
| Call audio error correction (libopus in-band FEC) | Off | Settings › Advanced › Experiments › "Call audio error correction", Android `test_call_native_opus`: 10 % loss hint, constrained VBR, the frame before an arrived packet rebuilt with decode_fec |
| Rotating discovery IDs, phase 1 | Off | Settings › Privacy › Advanced privacy › "Rotating discovery IDs" (`experimentalRotatingIds`): call-ready presence advertises compact UUID v2 with a 15-minute role-0 RDI (P in the Keychain, monotonic epoch clock, 1-8 s boundary silence), BDO1 openings with link hello bit 3, the caller opening check, pins, the stranger tarpit and "Visible by your ID for 10 to 25 minutes". iOS cannot change the device name: the setting tells the user to rename the phone. Stream phase 1b is not built: while it is on, a rotating (version 5) stream is neither joined nor forwarded, because this phone's request and forwarder offer would carry its fixed prefix |
| Stream forwarding (viewer passes a live stream on to one child) | Off | Settings › "Relay live streams" (`experimentalRelayForOthers`). Video uses the existing BFG1 grant and keyframe recovery. Audio-only streams copy source-signed records unchanged, bootstrap BTL1 and OpusHead without a keyframe, and use Android preset-based admission, exact audio shedding, shed-rate/30 s withdrawal and parent-inbound protection with per-transport cooldown. Keep the app open for new listeners. Simulator/package tests only; real Bluetooth interoperability and background behavior remain unverified. |
| Call relay hop | Off | DEBUG launch argument `-NearbyRelayCallee <handle>` with the same switch, as Android's DEBUG-only `test_private_call_relay`. Downstream first, one parent and one child, bit 6 and maxChildren 1 in both link hellos, end-to-end records copied unchanged, heartbeats replaced with version-1 liveness, 180 s parent wait, relayed calls capped at 110 kbps video |
| Relayed calls (Experimental) | Off | Settings › Advanced privacy › "Relayed calls" (`experimentalRelayedCalls`; launch argument `-experimentalRelayedCalls YES`), as Android's `test_relayed_calls`. Off: no consent bit, no link-hello bit 4, no reach table, hop type 12 rejected, exactly as before. On: (target) a relayed call rings only with this on, labelled "via a phone nearby", every ring capped at 60 s; the own call offer carries the consent bit and every call link hello signs bit 4. (Caller) call offers and reach pages (v4, and v6 with rotating IDs) from this device's own scans fill the reach tables; a saved contact with no direct offer but a relayed route is listed "Via N phone(s) · not confirmed"; dialling it connects to the first helper, sends `SETUP` and starts the call after `READY`; a route that fails before `READY` tries the next helper (at most 3 within 60 s of the tap); a Contacts call to someone not listed waits up to 45 s for a direct or relayed row. (Helper) sub-switch "Let phones nearby relay calls to me" (`relayedCallsConsent`, on within the experiment, Android `relayed_calls_consent`): the consent bit and whether relayed calls may ring; off, the first end-to-end record from a relay is refused unanswered. Sub-switch "Help calls nearby" (`relayedCallsHelp`, preselected on within the experiment, Android `relayed_calls_help`): while idle and not paused (Low Power Mode, iPhone battery under 20 % unplugged) the call offer carries the helper flag and the call listener signs link bits 4 and 6 with capacity 1; a first record SETUP from a parent that signed bit 4 hands the link to a relay duty (admission in protocol order, 3 per parent and 10 per minute, a pseudonymous parent in one shared bucket, a rotating helper answers message 1 with FAIL 5), which dials the next hop from this device's own reach table (BMH3 declared throwaway as a pseudonymous relay edge in pseudonym mode), answers READY or FAIL and copies the call opaquely; the offer is withdrawn while relaying, an incoming call is declined as busy, and the user's own call ends the relay. Apple cannot advertise reach pages (CoreBluetooth has no manufacturer data), so callers find an Apple helper only through searches (route searches) |
| Relayed calls: no direct sightings (DEBUG lab mask) | Off | Launch argument `-relayedNoDirect YES`, as Android's `test_relayed_calls_no_direct`: the reach tables ignore every target's own offer, as if no target were in range, so a co-located test can force a relayed route |
| Relayed calls: route searches (Experimental) | Off | Launch argument `-relayedOnDemand YES`, as Android's DEBUG `test_relayed_on_demand`; effective only with Relayed calls, Help calls nearby, Hidden identities and rotating IDs on. While helping and within its search budgets (rolling 10 minutes: 60 s duty, 30 s scanning, 12 dials, 12 handshakes, 10 s between searches) the call listener signs BMH3 `RELAY_SEEK`; a first record `SEEK` is answered from what this device heard (an offer in the last 5 s, else up to 3 s more of its scan): the target whose role-0 RDI gives the token (its opening checked), or for budget 2 up to two next helpers outside the skip list with a regenerated `SEEK`; at most 3 dials; FAILs are cached 60 s. This is how callers find an Apple helper, which cannot advertise reach pages. As caller (same switch, plus rotating IDs and hidden identities): a Contacts call to someone not listed also starts a search when the contact's lease window and a version 5 helper heard in the last 10 s exist. Ring 1 asks each first hop (up to 3: the helper that last reached this contact in this epoch, then signal) for budget 1 with the primary selector (the epoch of a direct recognition, else the lease centre); ring 1b uses the neighbour epoch inside 120 s of a boundary; ring 2 asks for budget 2 with the first hops that answered FAIL 1 as the skip list. A hop that answered FAIL 2 or 5, failed its binding or lacked RELAY_SEEK is not asked again; "no route" is remembered 60 s; each request needs its minimum allowance; the attempt ends at READY, at 45 s, or when the contact's own offer appears (then it is called directly). The search planner tries addresses heard twice first, then signal |
| Relayed stranger calls | On | Control arm only: launch argument `-relayedStrangerCalls NO` (Android `test_relayed_stranger_calls`). Off: a relayed call from an unverified stranger (a throwaway end-to-end key) is declined before it rings; on, it rings with the notice that answering reveals this phone's identity to whoever holds the call, which may be a relaying phone |
| Pseudonymous relay edges (Experimental relayed calls) | On | Control arm only: launch argument `-relayedPseudonymousEdges NO` (Android `test_relayed_pseudonymous_edges`). In pseudonym mode the call relay hop's child edge always speaks BMH3 with a declared throwaway, fresh per connection, no tag, nothing pinned; a child answering with a real key must be the callee at route cost 0, a declared throwaway is not bound (the caller's end-to-end check authenticates the callee). Toward a relay the caller's fresh link key declares PSEUDONYM. Off: the earlier behaviour, where the relay's real key met a pseudonym-mode callee's throwaway and the call failed |
| Hidden identities (BMH3 calls) | Off | Settings › Privacy › Advanced privacy › "Hidden identities" (`experimentalBmh3`, Android `bmh3`, which Android ships on). Needed to call Android phones with their default settings; off on the iPhone until phone tests pass. Prefixes that completed BMH3 are pinned for 30 days in a file outside backups (as Android), so a stripped hint cannot downgrade them to BMH2 after a restart |
| Pseudonymous toward strangers | Off | Under Hidden identities (`experimentalBmh3Pseudonyms`, Android `bmh3_pseudonyms`); needs Rotating discovery IDs. In this mode the phone neither speaks nor accepts BMH2 for calls |
| Relay: slow viewers skip to keyframes | On | Settings › Advanced › Experiments (`relayChildMediaAge`, Android `relay_child_media_age`, on by default there too); used only while Relay live streams is on |
| Stream link pacing, on-time seed raise, viewer on-time reports | On | Android defaults (`DebugTunables.linkPacing`, `onTimeSeedRaise`, `onTimeReports` are all on in Android release builds). Control arms for tests only: launch arguments `-linkPacing NO`, `-onTimeSeedRaise NO`, `-onTimeReports NO`; no Settings switch |
| Drop audio that arrived before the output started | On | `audioStartTrim`. The audio engine starts off the main thread (about a second on a Mac with voice processing), so a call can be active before playback runs. When playback starts, audio queued meanwhile is dropped down to the playout target (80 ms) and logged as `audio_backlog_dropped`; otherwise it would stay as extra delay for the whole call. Control arm for tests only: launch argument `-audioStartTrim NO` |
| Failed live joins: Try again and one automatic retry | On | `streamJoinRetry`, as Android `test_stream_join_retry`. A join that never got the source's header says "Couldn't join <title>." with Try again on the watch screen, and joins once by itself when the same stream (any route) is listed again within 30 s, only while that screen is open. Control arm for tests only: launch argument `-streamJoinRetry NO` |
| Crash reports on the next launch | On | `crashReports`, as Android's crash reports (on, "Don't ask again" in the prompt). MetricKit's crash diagnostics become a short scrubbed text (versions, device model, exception, the crashed thread's code locations; no names, IDs, paths or addresses) kept up to 7 days outside backups; the next launch shows it and asks to share it through the system share sheet. Nothing is sent automatically. Control arm for tests only: launch argument `-crashReports NO` |
| GATT lost-chunk fail-fast | On | As Android `test_gatt_gap_fast_fail` (ChunkGapPolicy): a GATT chunk gap held 1 s or behind 128 later chunks ends the link with "GATT chunk N was lost (M later chunks waited T ms)" instead of the call ending about 8 s later as "peer stopped responding". No wire change. Control arm for tests only: launch argument `-gattGapFastFail NO` |
| GATT lost-chunk recovery `GR1` (Experimental) | Off | Launch argument `-gattChunkRecovery YES`, as Android's DEBUG `test_gatt_chunk_recovery` (Android protocol reference "Draft: lost-chunk recovery"). Each GATT link keeps a 2 s history of sent values, announces it with a type-2 HELLO, answers NACKs with the stored value byte for byte (or GONE), probes an idle tail with HIGH, and its reader asks for missing chunks (3 rounds, 1 s deadline) once the peer's HELLO arrived; same constants as Android. Not yet run against phones |
| Aligned GATT values (Experimental) | Off | Launch argument `-gattAlignedValues YES`, as Android's `test_gatt_aligned_writes`; read when a GATT link opens and logged as `gatt_values` (limit, value, aligned). Writes and notifications use ATT values of whole 251-octet LE data PDUs: 495 bytes (two PDUs) instead of 512 (251 + 251 + 17), 244 below that, the limit itself below one PDU. Same chunk format, so no wire change. Android measured +44% goodput on a controller that sends one PDU per connection event as peripheral; untested on Apple controllers |
| Call audio coalescing (Experimental) | Off | Launch argument `-callAudioCoalesce YES`, as Android's `test_call_audio_coalesce`. When a 20 ms Opus unit leaves the call queue while more ordinary units already wait (audio that queued behind a slow link), they leave as one existing `BTA1` pair or `BTA2` batch (at most 20 units, 1 s span); nothing waits for audio not yet captured, so the added delay is zero. Every call receiver already splits pairs and batches. `call_stats` counts `audioCoalesced`. Not ported: Android's 40 ms pairs (`test_call_audio_pairs`, +10 ms mean delay) and AEAD cipher reuse (CryptoKit has no per-record provider lookup, and each record already reaches the link as one write) |
| Service discovery stall cut (Experimental) | Off | Launch argument `-servicesStallSeconds 4`. A first outgoing attempt still discovering services after that many seconds is closed and goes to the existing rediscover-and-retry; the retry keeps the 15 s timeout. Off by default: the 12 s and 15 s discovery hangs seen on Mac calls were macOS pairing prompts (the peer refused the GAP name read), and CoreBluetooth gives a central no pairing or encryption state, so the cut could abort a pairing the user is answering. Logged as `connect failedStage=services_stall` |
| Caller microphone prewarm (Experimental, macOS) | Off | Launch argument `-callerMicPrewarm YES`. At outgoingRinging the caller enables voice processing on an audio engine that is not started and has no tap (about 1.1 s on a Mac), so nothing is captured or sent before the call is active; the call's audio then starts on that engine. A call that ends first discards it. Only with the microphone already allowed. Logged as `audio_prewarm` (ready, used with ageMs, discarded) |
| Busy decline | On | Control arm: launch argument `-callBusyDecline NO` (close the link at once, as before). As Android: an incoming call while this device is in a call or dialling finishes its handshake and is declined with BUSY before it rings, with nothing shown, so the caller sees "Busy". Logged as `call_collision`. The busy listener is an ordinary hidden callee, so Android's glare exception (DialCollision) applies: while this device's own dial is still looking for its person (permissions, a dial wait, or a caller with no link yet), a call from that very person (its authenticated real prefix) rings instead and the own dial stops, so two devices dialling each other end in one call; `-dialCollisionRing NO` is its control arm (always busy) |
| Caller answer deadline | On | Control arm: launch argument `-callerAnswerDeadline NO`. As Android: a caller whose callee completed the handshakes but sent no Ringing within 15 s of hop authentication (relayed: the 20 s setup budget plus 10 s) ends the call with "The other phone connected but did not answer the call" instead of waiting for the 60 s ring timeout |
| Stream join keeps waiting after a bad connection | On | Control arm: launch argument `-watchKeepWaiting NO`. As Android: a connection to a viewer that fails before its hop handshake (a stranger, a stale dial, noise) is dropped and the join waits again within the same 45 s, instead of ending the join |
| Forwarder graceful end | On | Control arm: launch argument `-forwarderGracefulEnd NO`. As Android: when the source ended the stream, the forwarder lets its child receive the forwarded terminal record (the link closes once drained, at most 2.5 s); after an upstream loss the child link closes at once |
| End the call on a local media failure | On (as Android; not yet phone-tested on Apple) | Control arm: launch argument `-callEndOnMediaFailure NO` (the call stays up, silent, with the notice, as before). As Android's `endForLocalMediaFailure`: when this device's call audio cannot start or restart (no audio session, no Opus codec, no running playback engine) or video arrives that it has no decoder for, it hangs up with an error reason; the other phone shows "Their phone had a problem and ended the call" instead of a silent call or a lost link. Microphone and camera problems keep the call with a notice, and iOS refusing the session because another app holds audio is not a failure |
| Viewer measured link reports | On (as Android; not yet phone-tested on Apple) | Control arm: launch argument `-viewerLinkReports NO` (only the on-time reports). As Android viewers: the parent link's arrival rate is measured from record trains (a record of at least 8,000 bytes over at least 60 ms that began after an idle gap, first chunk not counted; the median of the last 10 s) and reported to the parent at most once a second after a new train, so a source or relay paces to what this link delivers. No adaptive playout clock: the report never says late or adds delay |
| Call picture rotation while the iPhone turns | On (as Android's display rotation; not yet phone-tested) | Control arm: launch argument `-callSendRotation NO`. While the call camera runs, the iPhone sends the BME1 display rotation (clockwise 0/90/180/270, the phone's turn from portrait; flat keeps the last) so the other phone shows a sideways-held picture upright. Not on the Mac, whose camera does not turn with it |
| Drop leading blank camera frames (Experimental) | Off | Launch argument `-dropLeadingBlankFrames YES`, as Android `test_drop_leading_blank_frames`: the camera's leading black buffers (mean luma below 1, chroma within 1 of 128) are dropped until the first real frame, at most 15 frames or 1 s after the first, so a viewer's first picture is not black. The check itself always runs and logs `camera_leading_blank: blank= dropped= firstRealMs=` once per camera start |
| Audio-only live streams | On | Android `audio_live` (on for everyone, no Settings row). Off: Go live does not show "Audio only", audio-only offers are not listed (offers with a malformed marker never are), and a viewer refuses a `BTL1` header as an unsupported header (Android `allowAudioOnly`). Control arm for tests only: launch argument `-audioLive NO` |
| Quick wipe gesture | Off | Settings › Privacy › "Quick wipe" (`quickWipeGesture`, Android `panic_wipe_gesture`): three quick taps on a tab title ask to erase. Off so a stray triple-tap erases nothing |
| Generated nearby names (iPhone and Mac) | On (2026-10-27, as Android) | Settings › Privacy › "Generated nearby names" (`experimentalDesktopGeneratedNames`; off is the control arm, launch argument `-experimentalDesktopGeneratedNames NO`); Android names-v2 labels for public rotating offers and authenticated throwaway callers, collision suffixes, and this Mac's advertised name in Calls/Settings. Own rotating advertising remains controlled by Rotating discovery IDs |
| Adapt call video to delivery (native macOS) | Off | Settings › Advanced › Experiments (`experimentalDesktopCallDeliveryFeedback`); uses the direct peer's existing version-3 delivery counters to measure queued video beyond the local transport buffer. Video goodput excludes the audio actually delivered. Legacy, invalid and stale reports retain local adaptation |
| Pause discovery during calls (native macOS) | Off | Settings › Advanced › Experiments (`experimentalDesktopPauseCallDiscovery`); stops the Mac's discovery scan only after a call link attaches, preserving outgoing address-refresh retries. Restores scanning on call termination and leaves stream/viewer discovery alone. A video call with it on still dropped after about 5.5 minutes; see [testing](testing.md#hardware-results-release-app-mac-with-android-phones-over-gatt) |
| Menu bar item (native macOS) | On | Settings › Desktop › Show in menu bar (`desktopShowMenuBar`). A `MenuBarExtra` shows Reachable, Not reachable, In call or Live (a template icon; red only for Live) with Open MeshLive, a Reachable for calls switch (the same Allow calls setting) and Quit. On by default because it only shows state and repeats existing controls: it starts no radio, media, activity or notification, and can be hidden |
| Keep running with windows closed (native macOS) | Off | Settings › Desktop (`desktopKeepRunningWithWindowClosed`). Bluetooth, calls and live streams keep running with all windows closed while the Mac is awake; Window › Show MeshLive returns, MeshLive › Quit stops. Off: closing the last window quits |
| Start at login (native macOS) | Off | Settings › Desktop › Start at login: `SMAppService.mainApp` register/unregister. The switch shows the system's status, including approval pending in System Settings › General › Login Items; MeshLive never registers itself. Not yet checked across a real logout/login with the ad-hoc signed build |
| Ring window in the background (native macOS) | Off | Settings › Desktop (`experimentalDesktopRingWindow`). While a call rings and another app is frontmost, a non-activating floating panel on every Space offers Decline, Voice (video calls) and Accept; Accept brings MeshLive forward. The local notification and the app's ringer are unchanged. Verified only with the preview fixture, not with a real incoming call |
| Stay active during calls and live (native macOS) | Off | Settings › Desktop (`experimentalDesktopActivityDuringMedia`). `ProcessInfo.beginActivity(.userInitiated)` (no App Nap, timer coalescing or idle system sleep) while a call rings or runs, while sending or watching/listening to a live stream or live audio, and while relaying a call; adds `.idleDisplaySleepDisabled` while video is on screen; ends when they stop. | Avoid App Nap while reachable (native macOS) | Off | Settings › Desktop (`experimentalDesktopNoAppNapWhileReachable`). `.userInitiatedAllowingIdleSystemSleep` while Bluetooth is ready and Allow calls is on, so link and discovery timers are not throttled behind other apps; the Mac may still idle-sleep. | Keep Mac awake while reachable (native macOS) | Off | Settings › Desktop (`desktopKeepAwakeWhileReachable`). `.userInitiated` while reachable: no idle system sleep (the display may sleep; closing the lid still sleeps the Mac). Optional battery tradeoff |
| Reachable only while the window is open (native macOS, Experimental) | Off | Settings › Desktop (`experimentalDesktopAdvertiseOnlyWithWindow`). Checked on the Mac: hide stops the call offer, unhide restores it; off, nothing changes |
| Time Sensitive call notifications (native macOS) | Off unless entitled | The incoming-call notification uses `.timeSensitive` only when the signed app carries Apple's `com.apple.developer.usernotifications.time-sensitive` entitlement (checked at run time); ad-hoc builds, which cannot carry it, keep `.active` |
