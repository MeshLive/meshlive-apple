# Wire protocol: iPhone notes

The canonical specification is [meshlive-android protocol reference](https://github.com/MeshLive/meshlive-android/blob/main/docs/dev/protocol/README.md). This file summarises what the iPhone implements and the iPhone-only parts.

The iPhone app speaks the Android app's protocol. The Android repository's protocol reference (`docs/dev/protocol/`) is authoritative. iPhone discovery uses the reviewed [addendum A](../../Interop/ANDROID_DISCOVERY_ADDENDUM.md); Android ships it behind `test_ios_compact_discovery` ("Experimental: find iPhones"), off by default. This file records the byte layouts as implemented in `Sources/NearbyCore` and checked against vectors produced by Android's own classes ([Interop/android-vectors](../../Interop/android-vectors/README.md)). Where this file and Android differ, Android wins and this file is a bug.

All integers are big-endian unless noted. Every parser is strict: wrong magic, length, version, type or trailing bytes fail closed.

## Discovery

| Item | Value |
| --- | --- |
| Android advertising data | 128-bit service UUID `C8D5A101-9F88-4F65-A03D-7F5A2FB921FA` |
| Android scan response | manufacturer data, company `0xFFFF`, 22-byte announcement |
| iPhone advertising | one 128-bit compact-announcement UUID (magic `0xC8D6`, addendum A) + local name of at most 8 bytes; one kind at a time, a pending viewer request beats call availability (review R5) |

22-byte announcement (version 2): `version 02 | nodePrefix 6 | flags 1 | capabilitySummary 1 | streamToken 4 | routeCost 1 | (sequence 1, width 2, height 2, fps 1 | or recoveryPrefix 6 when flags bit 7) | bitrateKbps 2`. Flags: 1 accepting connections, 2 relay capable, 4 stream available, 8 GATT transport (else LE CoC), 16 Classic, 32 stream paused, 64 private call available, 128 route recovery. Stream-offer `sequence`: bit 7 source full, bits 6..0 capacity generation. Route token = logical token (1..2^31-1) XOR FNV-1a-32 over `UTF8("bluetooth-video-route-v1") || prefix`, with bit 31 forced to 1. A viewer request copies the offer's route token. Announcements are unauthenticated hints; identity comes from BMH2.

Roles: a private-call callee and a stream **viewer** are peripherals (they advertise and accept); a caller and a stream **source** are centrals. iPhones act in both roles. iPhones scan without a service filter in the foreground (compact UUIDs differ per device) and parse both forms.

## GATT database and links

| UUID | Role |
| --- | --- |
| `C8D5A101-…` service, `C8D5A102-…` read | LE CoC: 2-byte big-endian PSM (dynamic; iPhone publishes with `publishL2CAPChannel(withEncryption: false)`, Android uses insecure CoC) |
| `C8D5A105-…` service | GATT data service |
| `C8D5A103-…` | central → peripheral, write and write-without-response |
| `C8D5A104-…` + CCCD | peripheral → central, notify; subscription admits one central |

LE CoC carries the byte stream directly. GATT carries it in chunks: each ATT value is `0x01 | u32 chunkSequence | payload`, sequences start at 0 per direction, payload = min(MTU-3, 512) - 5. Values starting `0x02` are ignored; duplicates are ignored and up to 4,096 early chunks are held for reordering (Android `GattBytePipe`). The iPhone writes without response, honouring `canSendWriteWithoutResponse`, and notifies honouring `updateValue` back-pressure.

## BMH2 handshakes

Link handshake on the raw stream: the initiator (central) writes `u32 length | hello`, the responder verifies it and answers the same way (length 1..2048). The endpoint handshake repeats the exchange inside BMS1 type 4 records with the end-to-end domain.

Hello: `"BMH2" | role (1 initiator, 2 responder) | nodeId 16 | u16 len + identity SPKI DER | u16 len + ephemeral SPKI DER | nonce 32 | capabilities 7 | u16 len + DER ECDSA-SHA256 signature`. The signature covers `context || hello-without-signature`; contexts are `BluetoothVideoMesh/LinkHandshake/1` and `BluetoothVideoMesh/EndToEndHandshake/1`. NodeId = SHA-256(identity SPKI)[0:16]. Keys: ECDH(P-256 ephemerals) x-coordinate; salt = SHA-256(initiatorNonce || responderNonce); info = `BluetoothVideoMesh/LinkSession/1` (or `…/EndToEndSession/1`) || SHA-256(initiatorHello || responderHello); HKDF-SHA-256 → 64 bytes: initiator→responder key, then responder→initiator key.

Capabilities: `version 01 | transportMask | encodeCodecMask | decodeCodecMask | u16 maxBitrateKbps | maxChildren`. Transport bits: 1 Classic, 2 LE CoC, 4 GATT, 64 call relay (link hello), 128 call video fragments (endpoint hello). Codec bits: 1 VP9, 2 AV1, 4 H.264, 8 HEVC (Design HC; H.264 and HEVC only with their AB5 masters on); decode-mask bit 128 "prefer VP9" and bit 16 "my AV1 decoding is software" (end-to-end call hellos; Apple never sets bit 16). Announcement summaries map codecs through one table (VP9 `0x01`, AV1 `0x02`, H.264 `0x04`, HEVC `0x80`); a hello mask is never copied into a summary. Each side requires the peer's link hello to sign the transport actually in use. The iPhone signs encode VP9 (libvpx) and decode VP9 (+ AV1 where VideoToolbox has hardware AV1; with the AB5 masters on, + HEVC and H.264 decode, and + H.264 or HEVC encode only when a VideoToolbox hardware encoder setup's output passed the receiver rules in the per-process probe), maxBitrate 1200 (CoC) / 1100 (GATT), maxChildren 0.

The iPhone identity is a P-256 key in the Secure Enclave (Keychain software key where none exists). CryptoKit's SPKI encoding is byte-identical to Java's, so node IDs and fingerprints match Android's.

## BMS1 hop records and BME1 endpoint content

BMS1: `"BMS1" | type | u64 sequence | u32 ciphertextLength | AES-256-GCM(ciphertext || 16-byte tag)`, the 17-byte header is the AAD, nonce = `00000000 || u64 sequence`, exact next sequence per direction. Types: 4 endpoint handshake, 5 endpoint content, 6 heartbeat, 7 mesh envelope, 8 group control, 9 route withdrawal, 10 withdrawal ack (11 store-and-forward is rejected).

BME1 (inside type 5, or inside a mesh envelope): `"BME1" | contentType | u64 sequence | flags | u32 ciphertextLength | ciphertext+tag`, header as AAD, endpoint keys; increasing gaps allowed, replay/reorder rejected. Content types: 1 stream header, 2 media packet, 4 lifecycle (`LIVE 1`, `PAUSED 2`, `ENDED 3`), 5 keyframe request (empty), 6 private-call signal, 7 group key / forwarded-stream grant, 8 terminal ack (empty), 9 call video fragment (only if advertised), 12 in-call link renewal (Experimental, only after both end-to-end hellos signed bit 4). Only media/fragments may carry flags.

Heartbeats (type 6): `01` liveness; version 2 `02 | u16 arrivalKbps | flags | u16 addedDelayMs` (6 bytes); version 3 adds `u32 receivedMediaBytes | u32 linkClockMs` (14 bytes, flag bit 1 delivery-only). A call endpoint sends one `01` after the endpoint handshake to announce it accepts version 3; the iPhone sends version 3 only to a direct call peer that sent that `01`, otherwise version 2, every second. Stream viewers send `01` every 2 s. Silent-link timeouts: call 8 s; stream 8 s (CoC) / 6 s (GATT).

## Calls (BMC2)

Signal payload (23 bytes): `"BMC2" | signal | callId 16 | reason | relayHops`. Signals: 1 invite, 2 ringing, 3 accept, 4 decline (reason 1 rejected, 2 busy, 3 unsupported), 5 cancel, 6 hang-up (4 normal, 5 error), 7/8 camera off/on, 9/10 microphone muted/unmuted. Only Invite carries relay hops.

Sequence (caller = link and endpoint initiator): both sides send heartbeat `01`; caller sends Invite (voice call: Invite then Camera off); callee replies Ringing; on Accept (voice answer: Accept then Camera off) each side sends its BTV3 header (with Opus), then the Opus configuration packet, then media. A remote header moves the call to active. The header codec must be in the sender's signed encode mask and the receiver's decode mask; the sender chooses a codec the peer decodes (VP9 preference bit first). With an AB5 master on, the sender follows Android's Design HC call order instead: hardware HEVC, then libvpx VP9, then hardware H.264, only codecs in the peer's signed decode mask and in this device's signed encode mask; peer bit 128 puts VP9 first below only hardware HEVC; Low Power Mode or a warm device (thermal state fair or worse) at call start moves hardware H.264 above libvpx. Push-to-talk: holding sends Microphone unmuted, releasing sends Microphone muted; muted audio is not sent. Video fragments (type 9: `u32 total | u32 offset | chunk`, 2,048-byte chunks for packets over 3,072 bytes, only audio may interleave) are on for direct Bluetooth LE GATT calls on both platforms (Android since 2026-10-11): an endpoint signs bit 128 in its end-to-end hello only on a direct GATT call and sends fragments only when the peer signed it too.

## In-call link renewal (Design SR, Experimental, off)

As Android's "Experimental in-call link renewal" (the constants there are the contract; Android `CallLinkRenewal.kt`,
Windows WP10). A direct GATT call whose one direction stalled replaces its hop link and keeps the call: the call ID, the
call state and the end-to-end `BME1` session (keys and sequences) continue. DEBUG launch argument
`-appleLinkRenewal YES` (off in release builds until the release-build device check passes).

- **Capability and key.** With the switch on, a call's end-to-end hello signs bit 4 (`0x10`), except in a BVMID2 scan
  and while the AW1 Wi-Fi guest is on (its cutover events for a renewal are not wired on Apple, so the two never run in
  one call). Type 12 parses only when both hellos carried the bit. Both handshakes (BMH2 and BMH3) derive
  `K_renew = HKDF-SHA-256(min(k1, k2) || max(k1, k2), "BluetoothVideoMesh/SR1", "renew-key", 32)` from the two content
  keys only then; a verification session zeroes it at once, the end of the call zeroes it.
- **Records** (`RENEW`, type 12, flags 0): `OFFER` ticket | role (10 bytes), `ARMED` ticket (9), `REFUSED` ticket |
  reason 1-7 (10), `BIND` ticket | next send sequence (17, its own BME1 sequence plus one). Any other op or length, a
  zero ticket, a role above 1, a reason outside 1-7 or a BIND sequence of 0 fails closed.
- **Advert and opening.** UUID = `HMAC(K_renew, "SR1 srv" | callId | ticket)[0:16]` with version 4 and variant `10`.
  On the new GATT link, before any BMS1 byte: `SR1C` challenge (20 bytes, armed side, on subscription), `SR1P` ticket |
  nonce | MAC (60), `SR1A` MAC (36); hop keys `HKDF(K_renew, challenge | nonce, "SR1 hop" | callId | ticket, 64)`,
  bytes 0-31 offerer to armed. BMS1 restarts at sequence 0 with those keys; no BMH2 or BMH3 runs on the new link.
- **Sequence and bounds** (Android's): offer after 3 s of silence while own writes still complete plus 1 s, only in
  `ACTIVE` for 10 s, 2 attempts per call, 60 s apart; scan 6 s; break the old link only after the advert was seen;
  no connect after 11 s; the offerer ends the call 12 s after its offer without a bind; the armed phone stops
  advertising after 7 s and at 12 s disarms (old link alive) or ends the call (old link gone); at most 8 challenged
  connections, 1 s for a proof, one consumed ticket, BIND only as the first record of the proved connection. A peer
  heard again before the break abandons the renewal (`REFUSED` 7). On a collision the caller keeps its offer. While a
  renewal is possible the 8 s silence close is kept up to 14 s while this device's own writes still complete (Android
  stall tolerance). After BIND both sides drop a half-sent or half-received fragmented frame, request and send a key
  frame, and send their current microphone and camera signals and their LABELS record once more.
- **Apple radio.** The armed device keeps its one GATT database (the offerer connects to the usual data service, as on
  Android and Windows). From `OFFER` until the attempt ends it advertises only the derived UUID (for the 7 s window)
  and then nothing; its discovery advert comes back only when the attempt ends. While armed every new subscription is
  a renewal connection and gets a challenge at once, except a central that still holds a live server link of this
  device; a connection whose first bytes are not `SR1P` is dropped at once. The offerer's scan is filtered on the
  derived UUID (it then also reports in the background) and connects to the first sighting.
- **No fresh address on Apple.** CoreBluetooth cannot make a fresh advertising set or address, nor clear the
  discoverable flags: the renewal advert uses the device's current address (logged `nonDiscoverable=false`,
  `addressKind=unknown`). So an Apple armed device is the same peripheral, at the same address, as the link that
  stalled. An Apple offerer whose advertiser is the peripheral of the link it just broke waits, within its connect
  budget, for that connection's disconnect before it connects (`connect_start existing=true`, then `connect_waited`);
  an Android or Windows offerer must likewise finish its old connection first, since two LE connections between the
  same two addresses are not possible. Whether the renewed link can ride the stalled connection on Apple <-> Apple is
  unmeasured. A backgrounded iPhone moves the UUID to the overflow area, where Android and Windows cannot see it: an
  armed iPhone renews only in the foreground.
- **Privacy residual on Apple (not Android's fresh-set guarantee).** The UUID itself is unlinkable: a keyed value of
  the call and the attempt's ticket, so it links neither to this device nor to earlier calls. The radio around it is
  not: on Apple the same device, at the same address, stops its discovery advert and advertises an opaque connectable
  service, so a scanner can correlate the two by address and timing and learns that this device is in a call that is
  renewing; a subscriber receives the distinctive `SR1C` challenge and sees MeshLive's fixed GATT service and
  characteristic UUIDs. `addressKind=unknown` is no evidence of a resolvable private address or of a fresh one. The
  on-air advertising and scan-response contents and the address behaviour must be checked on hardware before the
  switch is promoted.
- **What SR1 proves.** The opening authenticates the call's existing end-to-end peer (only the two endpoints hold
  `K_renew`; fresh challenge and nonce, distinct offer and armed labels, call ID and single-use ticket stop replay,
  reflection and rebinding). It does not prove the physical GATT path or proximity: a live relay can copy the advert
  and forward the whole opening and BMS1 byte stream between the real endpoints. That can move the radio path, expose
  timing or deny service (including consuming a valid ticket and dropping `CONFIRM`); it cannot change the inherited
  peer identity or learn the call or hop keys. A failed copied-advert connection is retried while time remains.
- **Clocks and keys.** "No record for 3 s" and the renewal's liveness count complete authenticated hop records only
  (partial bytes never postpone them); "own writes still complete" is the transport's completed writes (a GATT value
  written or a notification accepted), not records handed to it. Openings use the call's `K_renew` owner, never a
  copy, and fail once the call ended and zeroed it; the new link's hop keys are wiped once the link is built. The
  1 s proof window is judged at the proof's arrival; renewal deadlines run in the run loop's common modes.
- **One connection between two devices.** A device-round result (2026-11-10): with Android armed, an Apple offerer
  that connected the sighting got the connection but never the service discovery, in every case. Apple keeps one
  address, so this is a second LE connection to a device that still holds (or has just dropped) the old one; Android
  serves it no GATT. An Android offerer toward an Apple device already re-uses the existing connection, and that
  direction passed. So an Apple offerer now runs the renewed link over the LE connection that already exists to the
  armed device: it unsubscribes the old link (keeping its connection, when it was the central) or connects to the old
  link's central (when it was the peripheral), and subscribes to the armed device's own instance of the data service
  (the last instance; an Android armed phone adds one for the attempt, the old link's is never taken). A failed attempt
  is followed by one to the sighting, after letting the old connection go; the attempts alternate within the 11 s
  budget, each with a 3 s service-discovery cut (`call_renewal phase=connect_start via=existing_connection`,
  `phase=instances count=`). DEBUG control arm `-renewalOverExistingConnection NO`: every attempt connects the
  sighting. The wire bytes are unchanged; the armed side sees an ordinary new subscription.
- **A new stream on the same connection (Apple armed).** An offerer that re-uses the LE connection of a link on which
  it was already subscribed starts a new GATT stream without a new subscription (CoreBluetooth reports none). An Apple
  armed device therefore takes a GR1 HELLO that arrives on an established server link while it is armed as a new
  renewal connection: the old link ends there and the new stream gets its challenge (`phase=same_connection_stream`).
  Without GR1 on that link this case cannot be seen and the renewal ends at its bound.
- **One central at a time.** The renewed incoming link takes the old one's place, so during the call the one-central
  rule refuses other incoming GATT links exactly as before the renewal (calls already refuse them).
- **Interpretations.** A record cut off with the old link is lost (the protocol rule); Apple's queue hands records to the
  transport only while less than 4 KiB waits, and re-sends nothing else. A reveal goes before `ACTIVE`, at least 10 s
  before any renewal can start, so the reveal re-send rule never applies.
- **Logs:** `call_renewal` (`role`, `phase`, `reason`, `ms`, `attempt`) and `call_renewal_silence` (`role`, `ms`);
  DEBUG `-callTxStallAfterS N` (Android `test_call_tx_stall_after_s`) stops this device's call writer on its first link
  N s after the call became `ACTIVE` (`call_debug_tx_stall`).

## Wi-Fi Direct guest on iPhone and Mac (AW1, Experimental)

Scope: direct private calls whose link is BMH3 (no relay and `!isRelayed`). Apple joins an Android phone's Wi-Fi Direct group as a guest and never hosts; relayed calls, stream hops, Windows hosts and an Apple host are out of scope. The wire is Android's, unchanged: no new record, kind, bit or field. The build gate `wifiWire` and the user switches `wifiCarrier`/`wifiDirect` are all off by default.

- **CAPS and roles.** The link responder sends `CAPS` first once the call is ACTIVE and every reveal has verified; the initiator answers. Apple sets bit 3 ("Wi-Fi Direct client possible now") only when both switches are on, a call key `UW` exists and the platform can join now. Apple never offers Aware and never hosts, so with an Android host the chosen tuple is bearer 2 with Apple as guest. A call with only one revealed identity stays on Bluetooth.
- **HOST and CREDS.** Android sends `HOST(bearer 2, ticket, validMs, freqMhz)` then `CREDS(ticket, port, ipv4)` on carrier 0. Apple's guest `DECLINE`s in Android's order (1 no `UW`, 2 not the guest tuple, 1 non-direct bearer/`validMs`/reused ticket, 2 an attempt or carrier exists, 4 six hosts or under 29 s since the last attempt, 1 foreground/eligibility, and so on). `CREDS` is due within 8 s.
- **Join.** iPhone: `NEHotspotConfiguration(ssid:passphrase:isWEP:false)` with `joinOnce = false`; iOS prompts for every new network and exposes no band, so the guest uses the authenticated `HOST.freqMhz` (0 gives `DECLINE` 7). Mac: CoreWLAN scan then `associate(to:password:)`, band from `wlanChannel().channelBand` (2.4 GHz gives `DECLINE` 7); macOS Location is needed for scan results and is never read.
- **Pinning (F-4).** The joined interface is `en0` on iPhone and `CWWiFiClient...interfaceName` on Mac; its IPv4 address and prefix come from `getifaddrs`. `CREDS` must be a private on-link address that is not this device's, and no other interface may overlap the joined subnet (`DECLINE` 6 or 3). The socket is an `NWConnection` pinned to that interface and its IPv4 (`noDelay`, keep-alive off, 5 s timeout, refused connects retried every 250 ms).
- **Binding.** BWU1 guest: read frame 1 (21 bytes) within 2 s, write frame 2 (126), read frame 3 (102) within 2 s, derive `k_g2h`/`k_h2g`, write `BIND(role 1, ticket)` at once as BMS1 type 16, read the host's `BIND(role 2)`, write `READY(0xFFFF, 0, 0xFFFF)`, read the host's `READY`; all within connect + 5 s. Records after that use the same BMS1 sealer/opener from sequence 2. Without a call key (a BMH2 call) `UW` is nil: CAPS is all clear and every `HOST` gets `DECLINE` 1.
- **Carrier.** Wi-Fi carries BME1 content (type 5), heartbeats (type 6) and, after BIND/READY, `SWITCH`/`RESUME` (type 16); anything else closes the Wi-Fi carrier, never the call. Each side sends a heartbeat after 500 ms idle and closes after 2.5 s without an authenticated record, after a write stalled 2.5 s, or on a socket error. A `BMS1` header of type 16 outside 5 to 96 plaintext bytes is refused before its body arrives.
- **Cutover.** Boundaries are BME1 content sequences. After `READY`, a side moves its own direction with `SWITCH(gen, ticket, next sequence, 0)` sealed on Bluetooth under Android's conditions (ACTIVE 3 s, oldest queued record under 500 ms, no cooldown, fewer than 2 fallbacks); `RESUME` is sealed the same way before further Bluetooth output. The receiver applies the peer's `SWITCH`/`RESUME`, holds early Wi-Fi records (1 s or 5 MiB) and drops fenced ones. A loss falls back with `RESUME`, a keyframe and a 30 s cooldown. Held Wi-Fi records are released in order and only past the last delivered sequence. After a fallback or a hold promotion the receiver drops a half-received fragmented frame, skips fragments until a frame starts and asks the peer for a keyframe; a sender that falls back drops the unsent fragments of its current frame. A `DECLINE` naming a carrier that is already up is stale and ignored, as on Android. A join that completes after the call left it undoes itself (Mac: disassociate; iPhone: remove the configuration). `CLOSE` is never sent and is ignored.
- **Not in AW1.** No Apple host, no Aware, no quality fallback (Android's 300 ms/5 s goodput rule); a call whose Bluetooth link is lost ends even with Wi-Fi alive. Rates are unchanged: `READY` is informational only.
- **Logs.** `wifi_upgrade`, `wifi_caps` and `wifi_cutover` events; `call_stats` gains `wifiCarrier` (`none`/`binding`/`up`) and `wifiSending`. No SSID, password, ticket or address is logged.

## Wi-Fi Direct guest on stream hops (AW2, Experimental)

Scope: the viewer of a direct video stream (the parent sends `BME1` records, header `BTV3`). Apple joins the Android parent's Wi-Fi Direct group as a guest; Apple stream sources, forwarders, relaying viewers, forwarded routes and audio-only streams carry no Wi-Fi. The wire is Android's, unchanged. The gate is AW1's: `wifiWire`, then `wifiCarrier` or `wifiDirect`.

- **Gate (BMH2 hops).** With the switches on, the viewer's link hello carries Android's build tag (link-hello bit 7, nonce bytes 0-1 big-endian) with release 11 (`WIFI_FIRST_RELEASE`) and no release key. A hop may carry `BWF1` only when both link hellos carry a tag of at least 11; otherwise type 16 stays rejected. With the switches off nothing is signed and every byte is as before.
- **Hop key.** `UW_hop = HKDF-Expand(HKDF-Extract("BluetoothVideoMesh/WifiUpgrade/1/hop", min(kA, kB) | max(kA, kB)), "BluetoothVideoMesh/WifiUpgrade/1/key", 32)` from the link's two directional `BMS1` keys (unsigned bytewise order; equal keys refused), derived when the keys are installed and handed to the agent once.
- **CAPS and roles.** The child sends `CAPS` first, once, after its first stream header; the parent answers. The child is the link initiator of the role choice whichever side dialled, so an Android parent (bits 2 and 3) hosts and Apple (bit 3) is the guest. A relaying viewer, a forwarded route or an audio-only stream sends `CAPS` with every bit clear. The bits sent stay the offer for the hop.
- **Carrier and cutover.** `HOST`, `CREDS`, join, pinning, binding, liveness and fallback are AW1's. The viewer reads the parent's media from Wi-Fi from the parent's `SWITCH` boundary (a `BME1` content sequence), holds and releases early records, and asks the parent for a keyframe after a fallback or a hold promotion. It never moves its own direction: keyframe requests, end acknowledgements and reports stay on Bluetooth, and a lost carrier is announced with `RESUME`. The parent's Bluetooth heartbeats, written once its hop machine runs, are dropped as Android's stream child drops them. While media arrives on Wi-Fi the viewer reports on time (0 kbps, not late) instead of a Bluetooth-measured rate.
- **Not in AW2.** Apple as a stream parent or forwarder on Wi-Fi, mesh-envelope and relay hops, the child's own direction on Wi-Fi, a stream kept alive on Wi-Fi when Bluetooth dies, and the quality fallback.
- **Logs.** As AW1; `wifi_caps event=sent` carries `hop=stream` or `hop=call`.

## Streams (BTV3, BMV1, BFG1)

BTV3 header (15 bytes): `"BTV3" | u16 width | u16 height | fps | codec (2 VP9, 3 AV1; 4 H.264 and 5 HEVC only with their AB5 masters on) | rotation quarter-turns | audioCodec (0 none, 1 Opus) | u16 sampleRate (48000) | channels (1)`. Media packet: `i32 payloadLength | flags | i64 ptsMicroseconds | payload`; flags 1 codec config, 2 keyframe, 4 display rotation (1-byte quarter-turns payload), 8 audio, 32 discontinuity, 64 audio pair/batch, 128 discardable. The inner flags must equal the BME1 header flags. Audio: raw 20 ms Opus packets at 48 kHz mono; the first audio packet is a codec configuration carrying a 19-byte `OpusHead` (Android may send `AOPUSHDR` blocks; the iPhone ignores either). Pairs `"BTA1" | i32 delta | u16 len + unit | u16 len + unit` and batches `"BTA2" | count 3..20 | (i32 delta | u16 len + unit)*` are split on receipt. Audio and video share one monotonic microsecond timeline.

Viewer (link and endpoint responder): if the source's link hello signs `maxChildren > 1` (BGK1 group relay) the iPhone refuses. If the endpoint signs `maxChildren > 0` it is a viewer-forwarder: the next record is a type-7 content holding `"BFG1" | sourceNodeId 16 | streamId 16 | mediaKey 32`, and media arrive as mesh envelopes opened with that key. Mesh envelope (BMS1 type 7): `"BMV1" | streamId 16 | sourceNodeId 16 | u64 sequence | ttl | flags | u32 length | sealed BME1`; source must match, sequence strictly increases, duplicates rejected. The viewer sends keyframe requests and heartbeats, answers ENDED with a terminal ack and a route withdrawal (type 9, `01` local capacity) with a type-10 ack. Source (link and endpoint initiator): header first, then config/media; direct BME1 records, or mesh envelopes (TTL 8) when the viewer signed `maxChildren` 1; pause clears queued media and repeats PAUSED every 2 s; end sends ENDED and waits up to 2 s for the ack.

## Identity verification and wipe

Fingerprint = SHA-256(identity SPKI), shown as 16 groups of four hex digits. Safety code: `h1 = SHA-512("BluetoothVideoMesh/IdentityVerification/SafetyCode/2" || fp)`, `h(i+1) = SHA-512(h(i) || fp)` to `h5200`; six 40-bit groups mod 100000 per half; the pair code is both halves sorted (60 digits). Static code (older): `BVMID1.<64 hex>.<base64url NFC name>`, strict parser; still read, and shown only when BVMID2 cannot run (rotating IDs or hidden identities off). A contact is marked verified only if the scanned/confirmed fingerprint equals one authenticated in this process; a verified contact's prefix with another key refuses the endpoint (always). A BVMID1 scan records "Checked by code" (`safety-code`), never the shield, unless the DEBUG compat arm `-bvmid1Compat YES` (Android `bvmid1_compat`) is on, because a static code has no freshness. Emergency wipe: pending marker, Keychain items first (identity, contacts key), then files and settings, a second sweep, marker removed only when complete; it resumes on the next launch. Triple-tap on the home title is the panic gesture.

## Verification code BVMID2 (as Android, on, no switch)

`BVMID2.<64 hex fingerprint>.<64 hex K_qr>.<12 hex RDI>` (149 characters, uppercase hex and `.`; the parser takes one case only and refuses other versions, field counts, lengths, alphabets and an all-zero `K_qr`, with Android's reasons). No name and no epoch. The shared conformance vectors (`Tests/NearbyCoreTests/Fixtures/bvmid2.json`, bvmid2-011..015) and the BMH3 fixture's `K_QR`/`K_TAG_QR` and `link_qr_tag` vector are replayed byte for byte (`Bvmid2Tests`, `Bmh3VectorTests`).

- **Secret and tag:** `K_qr` is 32 fresh random bytes held in memory; `K_tag = HKDF-Expand(K_qr, "BluetoothVideoMesh/BMH3/QrTag/1", 32)`, used where a lease tag key is used, bound to `RDI | role 0 | epoch 0`.
- **Lifetime:** 300 s of monotonic time, the first completed use, the RDI changing (a new code on the new ID), or leaving the screen (page closed, app in the background, the code side hidden). One code at a time. While a code shows, the device advertises its role-0 call offer even with "Allow calls" off; then (`screenOnlyReachable`) it accepts nothing but a connection whose tag matches the code: an untagged or lease-tagged msg1 is closed before a key is drawn, a BMH2 hello is refused, and a link that did not match the code ends before any ring.
- **Displayer (`QrCodeDisplay`, one `QrConnectionGate` per incoming connection):** at msg1, before any key is drawn, a replayed first message closes silently; a consumed code raises the reuse alert and closes; the link handshake reserves the code (spending the Meet screen's own budget, 3 tokens, one per 10 s, and one of 3 attempts per code); a second connection while reserved is "busy"; the end-to-end handshake of the same connection continues under the reservation and is refused without it; a failed connection releases it; a reservation not committed within 45 s expires; the completed end-to-end handshake commits it. A code tag is not a lease: the lease-recipient rule does not apply to it. A code matched at one layer only ends the connection.
- **Scanner:** after parsing, it looks for call offers carrying the code's RDI at route cost 0 for 10 s and tries every advertising peripheral that carries it in turn (within 30 s), then connects as a caller with BMH3 R_FIRST, the code's tag at both layers, the real key, `expectedPeer` = the code's node ID, a pseudonym answer refused, and the handshake key's fingerprint equal to the code's before this device presents its own key; the advert's opening is checked as for a call.
- **Verify-only session (`QrSessionScope`):** link records end-to-end handshake, end-to-end content, heartbeats and BDO1 only; content `LABELS` (not shown or kept) and, with both endpoint hellos carrying bit 3, one `RECOGNITION_OFFER` and one `PRESENCE_LEASE` per direction; an Invite, any call signal, OPENING, reveal, media, key-frame request or a second OFFER/LEASE closes it. No ring, no Recent entry. It ends at a fixed 60 s, 20 s without the scanner's answer (scanner) or the scanner's OFFER (displayer), 2 s after nothing more can move, or at once on "No".
- **Mutual completion:** the shield only after this device scanned the code, the fingerprint matched and the user answered "Is this <name>'s screen?" with yes; "<name> scanned your code" from the displayer's commit; "scanned each other" when both happened in one visit (kept with the contact).
- **Leases (Design QL):** the scanner offers after its user's yes; the displayer never offers at the commit and answers the scanner's OFFER only when this connection committed the code, its own user confirmed that scanner during the current visit of Add contact, the scanner showed its real key and the link peer is the endpoint peer; a reuse alert withholds every lease not yet sent for the rest of the visit. So the first of two scans moves no lease and the second moves both. A contact only checked by code neither offers nor receives new leases until both phones scanned each other.
- **Consent (Design QL revision 2, no new bytes):** the scanner's confirmation carries "Let <name>'s phone recognise yours nearby" (default on). The answer is stored in that contact's "Can see when I'm nearby" after the shield and before the session may offer; a no or a failed write withholds the OFFER, so neither side stores a lease, and there is no decline record (the peer sees the session end without an OFFER, as for a late answer, an older build or a lost link). On both roles an OFFER or LEASE of a verification session leaves only for a person this device's user confirmed and let recognise it during the current visit of Add contact (checked when the side starts and again when each record is sent), and a side that withheld its OFFER sends no LEASE, even when the peer offered first. Call now after a stored lease is a new ordinary call; the verification session never carries an Invite.

## Media formats used by the iPhone

| Direction | Format |
| --- | --- |
| iPhone → Android video | VP9 profile 0, libvpx real-time CBR, keyframes on demand, portrait 240×426 (calls) / 360×640 (live), 15 fps, rotation 0 |
| Android → iPhone video | VP9 via VideoToolbox (Apple's supplemental decoder, iOS 26.2+) or bundled libvpx; AV1 via VideoToolbox only with hardware AV1 (A17 Pro/M3 and later) |
| Audio both ways | Opus 48 kHz mono, 20 ms, 24 kbps calls / 32 kbps live |

**H.264 and HEVC (AB5/AB5B, Design HC; Experimental, off: DEBUG launch arguments `-NearbyH264 YES`, `-NearbyHEVC YES`).** Calls only on the sending side: a call sends VideoToolbox hardware H.264 (High, Main or Constrained Baseline) or HEVC (Main) when the order above picks it and that codec passed the per-process probe; the live source stays VP9. The probe tries VideoToolbox setups in order (H.264: low-latency rate control, then standard; HEVC: low latency with every frame in the base layer, standard, standard with the base layer at the full frame rate, then low latency) and keeps the first whose eight test frames all pass the receiver's access-unit gate. VideoToolbox's low-latency rate control uses a temporal layer structure, which for HEVC signals temporal sub-layers that the gate refuses (rule 7, `vps_max_sub_layers_minus1` 0); the gate is never relaxed and no bitstream is rewritten, so where no HEVC setup passes, HEVC is decoded but not encoded (the AB5B report records the result on the test Mac). The bitstream is Android's: Annex B with 4-byte start codes, one access unit per `BTV3` video packet with exactly one slice, the VPS (HEVC), SPS and PPS before every IDR and in no other access unit, SEI, AUD and filler removed, no codec-config packet, the keyframe flag set from the NAL type, strictly increasing timestamps, keyframes every 60 s or on request (a request not answered by an IDR within 1 s is repeated; after 3 misses video stops with `no_idr` and the encoder is not used again in that process). Received codec 4/5 video (calls and streams) passes the access-unit gate (rules 1-11) before the decoder: a failed access unit is dropped and a keyframe is requested; a codec-config or discardable packet, or three rejected keyframes in 10 s, end the session. The decoder builds its format description from each keyframe's in-band sets and gets length-prefixed slices. Compact UUIDs carry VP9 and AV1 only while owner question Q-HC2 is open: bit 56 is never sent and HEVC cannot be announced, so an iPhone or Mac neither streams HEVC/H.264 nor offers to forward such a stream; it joins and watches Android HEVC and H.264 streams.

## Peer labels and Naming v2 label timing

On by default on both platforms (Android since 2026-10-17, iPhone and Mac since P5, with no switch; DEBUG `-experimentalPeerLabels NO` is the Apple control arm). The Android project's protocol reference ("Peer labels" and "Naming v2 / Label timing and audience") is canonical; vectors: `Interop/android-vectors/GenLabels.kt`.

- **Negotiation:** end-to-end hello transport bit 5 (`0x20`), never in link hellos. A sender writes content type 10 only when both endpoints set it; an opener that did not advertise it keeps rejecting type 10 (fail closed). On stream hops, labels travel only when the link peer is the endpoint.
- **BNL1 label:** `"BNL1" | version 1 | kind (1 name, 2 stream title, 3 call subject) | u16 SPKI length | SPKI | u32 sequence | binding type (1 call, 2 stream) | 16-byte call or stream ID | u8 text length | UTF-8 text | u16 signature length | DER ECDSA P-256 signature`. The signature covers `"BluetoothVideoMesh/Label/1" 0x00 || signed part` and uses the identity key. The receiver checks the signer against the authenticated endpoint (calls) or the grant's source (streams), the binding (the call ID, the grant stream ID, or 16 zero bytes on a direct stream), the signature, and that the text is already canonical. A call subject (kind 3) is never sent (decision 2026-11-05); a received kind-3 label is verified, decoded and dropped silently.
- **BLB1 container:** `"BLB1" | count 0..3 | (u16 length | BNL1)*`, sent as BME1 type 10. In calls, a callee buffers one container until Invite (R3). When each label goes is Naming v2 (`CallLabelPolicy`, adapted for Apple's decision of 2026-11-05: no call subject): the caller's name goes before Invite to a callee that presented its real key, unless that key is blocked; a callee behind a throwaway key (a stranger, with or without a selected offer) gets it only after its verified REVEAL and only if the revealed identity is not blocked, with "Who sees my name" read again at that moment (decision 2026-11-06, Android `CallerNameRelease`); Nobody sends nothing, Only my contacts only to a verified contact; a relayed real-key callee waits for its OPENING and is checked again then. Only the Experimental DEBUG launch argument `-namesBeforeAnswer YES` sends a stranger's name before Invite. The callee's name goes with Accept, at Ringing to a verified contact, and under Only my contacts only to a verified contact (in a stranger session after the caller's verified reveal); never with Nobody, and never on a declined, cancelled or unanswered call. In streams, one container (possibly empty) goes before the header, at a fixed position. Receivers keep the higher sequence and limit updates (2 s, 8 per minute).
- **Text rules:** trim, collapse whitespace, NFC; at most 32/48/64 UTF-8 bytes (name/title/subject). Reject: Cc/Cf/Co/Cs/Cn/Zl/Zp, more than 3 combining marks, check-mark symbols, handle-shaped text (R6), and scripts outside UTS #39 Moderately Restrictive (Unicode 15.0 Scripts.txt table, `Vendor/UNICODE-LICENSE.txt`). A person name also may not start or end with a tilde or a tilde look-alike, contain a tilde, a shield or lock symbol, " - ", or a comma or a middle dot (U+00B7 or a look-alike dot) followed by "seen", or read as a generated name after look-alike mapping (Android's minimal table on Apple), case folding and removing spaces and punctuation (Naming v2 reserved forms); a receiver drops such a label.
- **Title pages:** manufacturer payload `03 | route token u32 | digest u16 | index<<4 | count | 1-19 bytes`; never split a code point. They are shown "unconfirmed" until the signed title arrives; conflicting titles show none for 60 s. The iPhone reads them and cannot send manufacturer data.
- **R11:** in a compact call offer (kind 0), bit 18 means "may be relayed" and decodes as capabilitySummary `0x10`. Every other reserved bit still rejects. Vector: `C8D64010-2030-4050-60C0-000000040000`.

## Call blocking (local, no new bytes)

As Android (`CallBlocking.kt`, `PersonPolicy.kt`): a block is a full identity fingerprint. At the Invite, after the
relayed-call target rules and before the busy rule, a real-key caller on the list, or with "Block unknown callers" any
caller that is not a real-key verified contact, gets this phone's OPENING when one is due, the ordinary Ringing and,
after 3 s + random(0..4 s), the ordinary Decline (reason rejected); nothing rings or shows. A caller whose callee
presents the real key of a blocked person in the endpoint handshake (AB3, as Windows; stricter than Android, which only
withholds the caller's name) sends its Invite as usual and then treats the call as below. When a stranger's verified
`REVEAL` shows a blocked identity, either side sends nothing more (no label, no presence record, no media, and a caller
no reveal of its own), drops the other side's media, and ends the call after the same delay with the ordinary cancel or
hang-up. A viewer leaves a stream whose source proved a blocked identity (its own handshake identity or its `BTL1`
header identity). A forwarder's `BFG1` grant only names a source, so when it names a blocked one the viewer drops that
route for the rest of the watch and looks for the stream on another route (as Windows WP5F); the watch ends only when the
lost-stream search finds none. A source refuses a blocked viewer, a forwarder a blocked child, and a relay helper a blocked real-key parent.
The Live list hides only the cost-0 route attributed to a blocked or reported person (its fixed prefix, or the one
contact a rotating ID is recognised as) and routes whose source authenticated as blocked; another route of the same
logical token stays listed, because the token and the advertised ID are not authenticated (review 2026-11-06, as
Android and Windows). An unreadable block list blocks nobody and is shown with Reset (decision 2026-11-06).
A report keeps hiding the reported person (the attributed cost-0 route above, and routes whose source authenticates
as them), never a route by itself (AB3). "Hide this livestream" keeps a route key only when the viewer's hop proved the
advertised fixed ID, else it hides that advertiser's radio address for the run. Android hides a reported token on
every route (Android follow-up recorded). A call subject (label kind 3) is never sent; a received one
is decoded and dropped.

## Rotating discovery IDs (experimental, phase 1)

On by default on both platforms (Android since 0.2.0-beta, iPhone and Mac since 2026-11-04, with no switch; DEBUG `-experimentalRotatingIds NO` is the Apple control arm); the Android project's protocol reference (docs/dev/protocol/, "Experimental rotating discovery IDs") is canonical.

- **ID:** `e = floor(unix / 900)`, `w = floor(e / 672)`, `L_w = HMAC-SHA256(P, "BluetoothVideoMesh/Discovery/Lease/1" 0x00 || u32 w)`, `salt = HMAC-SHA256(L_w, "BluetoothVideoMesh/Discovery/Salt/1" 0x00 || u32 e || role)`, `RDI = SHA-256("BluetoothVideoMesh/Discovery/Id/1" 0x00 || nodeId || u32 e || role || salt)[0:6]`. P is 32 random bytes in the Keychain (this device only).
- **Adverts:** call-ready presence (role 0); a waiting viewer's request (role 2, below). Compact UUID v2 (version bits `10`, RDI in place of the prefix; every v1 reject rule applies) or Android announcement version 5. With rotating IDs turned off (DEBUG control arm only) both are rejected, except that the Mac's Android compatibility control arm can independently accept them while scanning. A rotating advert shows its generated name (no handle, and a contact only through a presence-lease recognition) before the handshake. Relayed rotating offers are not called in phase 1.
- **Streams (phase 1b, viewer side built):** a viewer request **mirrors the selected offer's version** (Android phase 1b item 2). A rotating (version 5 or compact v2) stream is joined with a **compact v2 viewer request** (kind 1, version bits `10`) carrying this device's role-2 RDI, the offer's route token (copied before the wait), route cost and bitrate, the offer's transport flag, codec summary 0 and no recovery hint (compact v2 has no field for one). The request rotates at each boundary while it waits (stop, uniform 1-8 s silence, the new epoch's role-2 ID; restarts inside an epoch reuse the epoch's ID) and has its own role-2 pins, evaluated when the source's connection is accepted; the viewer's `BDO1` carries those pinned role-2 entries, and it checks the connector's role-1 entry as before (endpoint node = link node). There is no downgrade: a rotating stream is never joined with the fixed prefix while rotating IDs are on; the DEBUG control arm `-rotatingViewer NO` refuses it instead (the app says why). A version 2 stream is joined with a compact v1 request and the notice "This source does not support private discovery. Your phone's fixed ID is visible while you join." (`rotid_downgrade`). **Source side (AB4; Experimental, off: DEBUG launch argument `-rotatingSource YES`).** A live offer is a compact v2 stream offer (kind 2) with this device's role-1 RDI and the route token `logical XOR mask(RDI)` (the logical token stays the stream's for its whole life), its bitrate rounded to the nearest 25 kbps as Android; it rotates at each boundary (stop, uniform 1-8 s silence, the new epoch's role-1 ID; restarts inside an epoch reuse it) and has its own role-1 pins, evaluated when a viewer link sends `BDO1`. Inside a Visible-by-handle window it is compact v1 with the fixed prefix, and the rotating offer comes back after a 1-8 s silence. With the switch on, every stream hop of the source signs link hello bit 3 and sends its pinned role-1 entries. The source answers a viewer request whose token is its current one or one of the two it replaced less than 60 s ago, on its own transport. A rotating request (compact v2, or Android's 22-byte version 5 scan response, which now decodes with or without a recovery hint) needs a role-2 entry that recomputes to the request's six bytes from the authenticated link node within two epochs of this device's wall epoch, and the endpoint must be that node; a viewer without bit 3 fails. A version 2 request keeps the prefix check (a `BDO1` that arrives anyway is read and ignored). Admission keys stay the advertising address and the announced bytes; a second authenticated link of the same node through a rotating request replaces the older one; a version 5 request's recovery hint is never read as a prefix and is not matched (an ordinary request). DEBUG `rotid_open: role=viewer | result=`. DEBUG launch argument `-NearbyRotidEpochS <60...900>` shortens the epoch for a phone test, as Android `test_rotid_epoch_s` (give both phones the same value; lease days stay real days). Not built yet: forwarder offers stay compact v1 (fixed prefix), so a rotating stream is not forwarded, and this device neither sends nor matches the recovery hint. With rotating IDs off (DEBUG only) the fixed prefix is public anyway, and a Mac with Android compatibility joins a rotating stream with its fixed identity.
- **Stream hop peer binding (SEC-B2):** on every live-stream hop (the source or forwarder that dials and the viewer that answers; version 2 and 5 offers; every transport) the authenticated end-to-end peer must be the authenticated link peer by full node ID, or the hop fails before any content. A viewer also checks the link peer's prefix against a selected version 2 offer before the end-to-end handshake. A forwarder runs its own end-to-end handshake with each child, so a forwarded stream needs no exception; there is no relay exemption on Apple. DEBUG `stream_peer_binding: result=mismatch | role=viewer|source|forwarder | version=2|5`.
- **Link opening:** call-endpoint link hellos set transport bit 3; when both do, the first hop record each way is exactly one `BDO1` (type 13): `"BDO1" | 01 | count 0..2 | (RDI 6 | epoch u32 | role u8 | salt 32)*`. Anywhere else type 13 is an unknown record. The responder sends only pinned role-0 entries (on air, or off air for less than 60 s); the initiator sends count 0.
- **Caller check:** a selected rotating advert needs bit 3 and an entry with role 0 whose RDI equals the selected bytes and recomputes from the authenticated link node ID, and the endpoint must be that link peer; a selected fixed advert keeps the prefix check.
- **Clock and rotation:** the monotonic epoch (tick on a wall boundary or after 960 s of monotonic time; never repeats; a forward pin above 96 epochs for 1 h starts a new generation). At a boundary the iPhone stops advertising for a uniform 1-8 s. The stranger tarpit delays a stranger's responder hello by `2^(n-6)` s (cap 30 s) per epoch, and an incoming call that rings forgives one.

## Presence leases (experimental, phase 2, with rotating IDs)

- **Keys:** independent random day keys `L_d` in the window `[dayOf(E - 1), dayOf(E) + 27]` (Android "Keys and epochs"), kept in one Keychain item (this device only), never derived from each other; every own salt is keyed by `L_d(e)`.
- **Exchange:** in an answered call between mutual verified contacts, BDX1 `RECOGNITION_OFFER` then `PRESENCE_LEASE` (28 days), real identities only (after both reveals in a pseudonym call). A recognised rotating advert shows the contact's label as "<label> · seen nearby · unconfirmed" (Android `people_seen_nearby`), never a check mark. With a held lease the caller tags BMH3 msg1 (`K_tag`), and both sides present real keys.
- **Revocation (a new generation, a whole new key window):** Settings > Advanced "Reset presence key"; turning a contact's "Can see when I'm nearby" off (contact sheet; not yet asked until the user answers, which counts as off, decision 2026-11-06) after it received a lease; forgetting such a contact; "Reset contacts" when any contact received a lease (every contact record, and with it this phone's recognition of former contacts, goes); the epoch forward-jump recovery. A revocation re-advertises at once with an ID from the new generation instead of waiting for the next boundary. At launch, records of contacts that are no longer verified are dropped the same way (Android `reconcile`).
- **Storage discipline (Android PresenceVault):** a Keychain read error is never taken for an empty vault: the phone advertises from an in-memory window, sends no OFFER, recognises nobody and retries the read, but never writes over the stored vault. The vault is replaced in place (a failed write keeps the old value). A guard record outside the vault (the highest generation used, the highest revoked one, a revocation pending while the generation is unknown, and switch-offs not yet stored, as HMAC-SHA256 of the node ID under a random 32-byte secret kept in the Keychain, this device only) is written before every revocation: the file is replaced atomically and flushed with `F_FULLFSYNC`, and a write counts as stored only when that flush and the flush of its directory succeed. A switch-off of a contact that holds the current lease records the switch-off and the revocation of the current generation in the guard first, then stores the new window with the switch-off in one vault write; the guard entry is cleared only after that. Guard formats of pre-release builds (none was distributed) are not migrated. At load, a stored vault at or below the revoked generation, below the floor, or loaded while a revocation is pending is replaced by a fresh window; if neither the guard nor the vault can be written during a revocation, the stored vault is deleted. Residual: a revocation made while the guard file cannot be written (and the vault is unreadable) lives only in memory until the app stops. Switch-offs, Forget, Reset contacts and the launch reconciliation made while the vault cannot be stored wait and are applied when it can; no lease goes to a contact whose switch-off waits. A vault that no longer decodes is kept until "Reset presence key" replaces it. Finished lease days are deleted from the store, not just from memory.
- **Reinstall (iPhone-specific):** iOS keeps Keychain items when the app is deleted, but not the app's files (verified contacts) or preferences. The first launch of a fresh install drops every contact record and starts a new generation, so phones that held the old keys recognise nothing. The emergency wipe deletes the vault (and the phase 1 presence key, which earlier builds left behind); it counts as finished only when every Keychain deletion succeeded or found nothing, a query then reports every service empty (an error is not absence) and the contacts, guard and pin files are gone, otherwise it resumes at the next launch.

## Relaying (experimental, off by default)

Ports of Android's hop-local relays; each phone acts only on its parent and its direct child.

- **Stream forwarding.** A viewer that joined through a discovered offer signs `maxChildren` 1 in its link hello, so the source sends BMV1 envelopes (`> 1` would select Android's BGK1 group path). After the header, admission compares the relay need, 2 x per-link load, with the relay budget. Per-link load is `(video + 32 + 13 x 8 x (fps + 25) / 1000) x 1.2` kbps. With no relay evidence (cold start, Android e676ae5) the budget is `max(measured, 2 x per-link)`, which admits exactly one child; an unknown offer bitrate admits without a check.
- **Onward offer.** The forwarder advertises a stream offer with the relay bit, route cost + 1, the codec bit, and its own route token (`logical ^ mask(own prefix)`). The iPhone sends it as a compact UUID, so Android children need "Experimental: find iPhones". It connects as central to the child's viewer request, runs fresh BMH2 link and endpoint handshakes as initiator, and sends BFG1 (`"BFG1" | source ID | stream ID | media-open key`, BME1 type 7).
- **Envelope copying.** Bootstrap: the header, the newest 8 codec configs and the latest stream state. Then live envelopes go out with only TTL - 1 changed, in strict sequence order. Until a keyframe, non-key video is skipped while audio and control pass. Child keyframe requests are regenerated upstream. ENDED is acknowledged upstream only after the child (2 s max). A child that stays behind live (2.5 s for 3 s, a 1.5 s growing trend, or 6 s) is withdrawn with `ROUTE_CONTROL` LOCAL_CAPACITY and a 4 s ack wait.
- **Call relay hop.** Downstream first: link initiator to the child (the callee at cost 0, or a relay that signs maxChildren 1 and bit 6), then the callee's offer with relay flag and cost + 1 for one parent (link responder). `END_TO_END_HANDSHAKE` and `END_TO_END_CONTENT` are copied unchanged in order; `LINK_HEARTBEAT` is replaced with version 1; any other record closes the relay. Invite carries hops = route cost (0-4), and relayed calls cap video at 110 kbps. The relayed offer keeps only the codec bits and the relay-consent bit 4 of the child's `capabilitySummary` (mask `0x17`); it clears the dual-listening hint (bit 3, Android d58b604) and the reserved bits, because a relay is single-bearer and the compact encoder rejects other bits. Offers with a rotating ID are not relayed in phase 1. Backpressure follows Android's blocking copy loop: the relay stops parsing one hop's records while 64 KiB of copied records wait for the other hop and resumes below 16 KiB (an LE CoC hop also stops reading, so its credits slow the sender); a hop that holds more than 512 KiB of unparsed input (a GATT peer cannot be slowed) ends the relay instead of buffering without limit.
